# 代码审查工作流

在本工作流调用依赖技能时，依赖提供实施方法；阶段、执行范围和验证深度以当前工作流、用户要求及项目规则为准。依赖中的全量测试、运行验收、文档更新或暂停要求先判断适用性，不因加载依赖就一律执行；项目明确的必需检查、安全约束和授权边界不得省略。

目标：沿真实调用链发现可行动的问题，验证测试是否能保护行为，给出与证据相称的结论。复用成熟 skills，不另建扫描框架或复制它们的完整清单。

## 1. 确定范围与依据

- 读取目标仓库及路径适用的 `AGENTS.md`、需求/接口契约、构建与 CI 配置。项目的架构规则、报告语言、发现筛选范围、覆盖率阈值、性能预算和必跑检查以这些来源为准，不在通用工作流里硬编码。
- 确认审查对象：PR/MR、提交区间、暂存/未暂存改动或指定模块。记录仓库、目标分支、base/head SHA；未提交改动须记录状态并在结束时确认未变化。
- PR/MR 按实际合并目标确定 merge-base，分清本次改动与目标分支自身变化；本地目标引用未刷新时说明限制。工作区审查同时检查相关未跟踪文件，不能仅看 `git diff`。
- 默认审查本次引入或暴露的问题；模块审计可包含存量问题。存量发现单列，无法确认归因时说明，不把猜测写成新回归。
- 先读测试了解意图，再完整阅读受影响实现，并搜索所有调用方：入口 → 权限/校验 → 业务 → 存储/外部调用 → 返回与副作用。共享函数需检查其他调用方，不能只审 ticket 提及的一条路径。
- 默认不修改源码、测试或配置。可以运行已确认安全的本地验证；复现所需临时文件放隔离位置。不因审查自动提交、推送、发评论、合并或部署。

审查调用链、间接影响与回归范围时，使用可用的[代码知识图谱](../development-workflow/references/code-knowledge-graph.md)辅助定位。核对索引版本及真实 diff，图谱结果不替代源码审查、行为断言或测试执行证据。

## 2. 按需要加载成熟 skills

从当前会话可用技能目录按名称定位并读取 `SKILL.md`，不要假定固定用户路径。下表是组合关系，不能把引用名称当作已经执行。

| Skill | 使用方式 |
|---|---|
| `code-review-and-quality` | 主审查框架：正确性、可读性、架构、安全与性能；先看测试，再看实现，最后核对验证证据。 |
| `test-driven-development` | 审查行为断言、边界/失败路径、测试隔离与回归保护；仅在获准补测或修复时进入 RED → GREEN。 |
| `security-and-hardening` | 涉及输入、身份/权限、敏感数据、外部调用、依赖或构建链时，追踪信任边界和可利用路径。 |
| `performance-optimization` | 涉及热点、数据规模、查询、并发、资源或性能承诺时，对比基线与候选版本的实际测量。 |
| `api-and-interface-design` | 接口、模块契约或兼容性变化时加载。 |
| `safe-structured-refactor` | 结构重构、事务归属或依赖方向变化时加载。 |
| `debugging-and-error-recovery` | 检查失败、证据矛盾或根因不明时加载。 |

所有维度均先做适用性判断；不适用项写明理由，适用但无法验证的项记为缺口。技能缺失时披露，使用本文完成能做的检查，不宣称执行过缺失技能。以审查模式使用各技能，不把实现/优化建议变成自动改代码的授权。

## 3. 审查测试覆盖率与有效性

先从仓库脚本、CI、测试配置识别真实命令、覆盖范围和排除项，复用已有工具；不默认某种语言、包管理器或全仓统一测试入口。

### 数字证据

- 分别记录工具支持的行/语句、分支、函数覆盖率；不支持的指标写“不支持”，未采集写“未测”。Go 语句覆盖率不能当作分支覆盖率。
- 区分全量、受影响模块与新增/修改行覆盖率。增量行覆盖率 = 已覆盖的变更可执行行 / 变更可执行行；只统计候选版本中的新增/修改可执行行，删除行不进入分母，分母为零写 N/A。
- 只用可靠的行映射或已有增量覆盖率工具给出百分比；没有映射时列出具体未覆盖位置，不伪造增量指标。
- 比较 base/head 时保持测试选择、工具版本、插桩范围与排除规则一致，并记录报告对应的 SHA。旧 CI 报告只能作为历史证据；源码变化后不能复用为当前验证。
- 检查未被 import 的源码是否进入覆盖率分母，是否新增忽略标记、跳过测试、缩小采集范围或删除断言以抬高数字。
- 阈值来自仓库配置。没有阈值就按业务风险判断，不自行设定 80%/90% 等通用合并线；总覆盖率高也不能抵消关键权限、资金或事务分支未验证。

### 行为证据

为受影响行为建立简短映射：`行为/风险 → 测试与断言 → 已验证/缺失`。

- 检查正常路径、空值/边界、错误传播和必要的拒绝路径；按变化补查超时/取消、重试、重复请求、并发和事务回滚。
- 确认测试断言业务结果和关键副作用，而非只有状态码、mock 调用或“未抛异常”；涉及集成契约时不能用全 mock 代替真实接线验证。
- 缺陷修复需要证据表明回归测试能识别旧缺陷、接受修复。必要时在隔离环境对旧实现复现；缺少 RED 证据如实写明，不能仅凭当前绿色就认定已证明。
- 检查测试是否真的被发现和执行，有无 skip、空断言、快照盲更、时间/顺序依赖。审查不等于要求每个函数新增测试；优先保护变更行为和高风险不变量。

## 4. 多维审查

| 维度 | 重点证据 |
|---|---|
| 正确性与数据完整性 | 需求/契约与实际结果一致；边界、错误传播、幂等、并发、事务回滚、写入与外部副作用顺序。 |
| 代码质量与架构 | 业务归属、依赖方向、类型边界、重复实现、死代码、复杂控制流和无收益抽象；先找已有能力和标准库。问题必须说明实际维护或行为影响，个人风格不阻断合并。 |
| 安全 | 不可信输入到危险操作的完整路径；认证与对象/租户级授权、注入、XSS、SSRF、文件/路径处理、敏感数据泄漏、资源滥用。按入口性质判断 CSRF、签名与重放风险。 |
| 依赖与供应链 | 锁文件/清单/CI 一致性、新依赖与安装脚本、已知漏洞对运行/构建/测试/部署路径的可达性；扫描结果逐项核实，不自动强制升级。 |
| 性能与资源 | N+1、查询/索引、无界读取或并发、重复工作、锁竞争、内存与连接泄漏、缓存失效/隔离、前端体积和渲染热点。 |
| 兼容性与运维 | API/数据格式、数据库迁移、配置默认值、混合版本部署、失败可观测性及回滚可行性；涉及 UI 时检查交互与基本可访问性。 |

安全发现提供入口、权限前提、数据流和影响，敏感证据脱敏。依赖漏洞记录扫描时间、工具和公告来源；查证当前公告时使用官方来源。扫描器通过不等于安全，未找到可达路径也不等于已证明不可达。

性能结论需要相同环境、数据规模、负载、缓存状态和测量方式的基线/候选结果；适当重复以区分噪声。记录与场景相关的延迟、吞吐、查询数或资源指标。仅有静态代码证据时写“性能风险待测”，不能声称性能已提升或没有退化。不为审查随意压测生产或添加优化。

## 5. 执行验证并归并发现

1. 运行最小相关测试，再执行仓库要求的 lint、类型检查、构建、测试、覆盖率及适用专项检查。先检查脚本和目标环境，避免测试连接真实业务数据或触发外部动作。只读审查使用不修改文件的检查方式；具体入口由项目提供。多仓库分别选择命令；集成测试、生成代码检查与单测分开记录。
2. 记录命令、工作目录、代码版本、退出结果、报告位置和关键输出；区分通过、失败、未运行和不适用。基础设施故障不能记为测试失败已归因，也不能记为通过。
3. 对失败追踪根因；必要时用相同条件验证基线。没有基线证据时不要武断称“原有问题”。避免更改用户当前工作树来复测旧版本。
4. 按根因合并重复发现，按影响排序。每项写清文件/准确行号、触发条件、实际影响、证据、最小修复方向和验证方法。证据不足的疑点进入待核实项。

严重程度与是否必改分别标记：

| 级别 | 含义 |
|---|---|
| P0 | 已有充分证据的紧急严重问题，如重大数据破坏或广泛可利用的严重漏洞；阻断。 |
| P1 | 重要业务不可用、安全/数据完整性受损或明确严重回归；通常必改。 |
| P2 | 特定条件下的真实缺陷或有证据的质量/性能问题；结合影响和项目规则标为必改或建议。 |
| P3 | 低影响改进建议；不因个人偏好阻断。 |

不要为凑数量输出问题，也不要把“缺少测试”直接写成“功能错误”。无发现时写“在本次范围和已执行验证内未发现可行动问题”，保留真实验证缺口。

## 6. 交付与修复复核

默认报告顺序：

1. **发现**：`[P1][必改] 文件:行 — 问题`，附触发条件、影响、证据、修复与验证建议。
2. **验证与覆盖率**：范围/base/head；各检查结果；可采集的覆盖指标、口径及关键未覆盖行为。
3. **待核实与剩余风险**：未执行的检查、缺失环境/证据、存量问题和需要补充的具体行动。
4. **结论**：通过 / 需修改 / 验证不足。结论仅限本次范围，审查通过不等于已合并、部署或线上验收。

- **通过**：无未解决必改项，适用的必需验证已通过，关键风险有证据；可以附非阻断建议。
- **需修改**：存在有证据的必改项或项目门禁不满足；验证缺口仍须列出。
- **验证不足**：尚无已确认阻断项，但关键验证缺失，不能判断可合并；不能写成“有条件通过”。

### 审查结果与自动化衔接

- 结果明确区分完整审查、专项结论和验证不足，并关联实际审查对象及版本；专项通过不能代表整体通过。
- 放行以项目规定的必需检查、审查和授权为准。具体平台、结果格式、触发机制和权限由项目接入定义，不在通用流程规定实现。
- 审查结论与普通讨论分开。对象和适用条件未变化时复用有效结论；出现新变化或反证时复核相关范围，不能因重新触发流程就重复全部审查。
- 发布审查结果可能触发外部动作时，先核对项目的接入方式与已有授权；规范本身不授予自动合并权限。

用户已授权修复时，复用开发工作流完成最小修复与必要回归测试，再重审修复 diff、受影响调用链及必要检查。逐项记录已修复/未修复/已授权延期；延期需说明风险、负责人和复查条件，不冒充修复。最终结论绑定最终版本，新增变化使相关旧结论失效。

默认单代理执行；只有用户或适用指令要求独立/并行审查时才分工。届时共享同一范围和版本、按测试/安全/性能等独立维度分配，主审逐项核实并去重，不按票数决定正确性。

## 调用示例

`使用 $code-review-workflow 审查当前分支相对目标分支的改动，检查测试覆盖率、代码质量、安全和性能，先只输出审查结果。`

`使用 $code-review-workflow 复核这个 MR，重点检查越权拒绝路径、事务失败覆盖和批量查询性能，并区分已验证与待验证项。`
