# Development Workflow

在本工作流调用依赖技能时，依赖提供实施方法；阶段、执行范围和验证深度以当前工作流、用户要求及项目规则为准。依赖中的全量测试、运行验收、文档更新或暂停要求先判断适用性，不因加载依赖就一律执行；项目明确的必需检查、安全约束和授权边界不得省略。

让每个开发步骤形成可验证的闭环，持续完成用户要求的范围。流程适用于不同语言、框架和平台；具体规范由当前项目提供，不固定分支名、工具、目录结构或代码长度阈值。

## 选择执行方式

- 以用户要求和已授权范围为准；“先看方案”只做分析，实施请求则推进到完成，不停在计划或示范步骤。
- 简单、局部且低风险的修改直接走精简闭环；跨模块或行为复杂的修改先列简短步骤；涉及权限、资金、并发、数据迁移等，先明确风险不变量和失败验证。
- 按行为、耦合和影响判断复杂度，不按文件数量判断。不默认创建计划文档、安装工具、启动多代理或要求逐阶段审批。
- 已有计划和有效验证证据继续使用；续接任务时确认变化，不重新执行整套流程。

按任务选择入口和验收重点，后续共享同一流程；混合任务分别标明行为变更与行为保持的范围。

| 任务 | 起点 → 完成依据 |
|---|---|
| 新功能 | 明确验收场景 → 完整路径产生预期结果 |
| 缺陷修复 | 复现或取得诊断证据 → 原问题消失且相关行为未回归 |
| 重构 | 建立原行为基线 → 行为保持且声明的结构目标达到 |
| 探索验证 | 明确假设与实验边界 → 得出有证据的结论，区分实验代码与交付代码 |

## 1. 澄清需求与验收结果

读取适用的 AGENTS.md、项目说明和相关架构约束。确认实际仓库、工作区改动、开发基线及用户要求的交付终点；没有版本控制时跳过 Git 步骤。

交付终点以用户要求为准。代码修改、可运行产物、提交、合并、部署和业务验收是不同终点；完成当前授权范围内的终点，不默认扩大，也不提前收尾。

从项目配置、现有测试和 CI 中确定构建、测试、格式与专项检查方式。多仓库工作区逐个识别相关 Git 根目录及服务门禁；区分只读检查与会自动修复的命令，运行前确认测试数据和外部副作用边界。规则缺失时采用已有惯例和最小合理做法，不自行生成治理体系。新项目尚无实现时，以当前需求和选定平台为起点，先做最小可运行路径，不预建未来架构。

实施前明确使用者或调用方、触发场景、可观察结果和不做范围，并能说明改变什么、保持什么、如何验证。能从代码确认的信息自行查明；不能用现有行为代替尚未明确的需求意图，只有影响正确性或范围的关键歧义才询问。保护已有工作，不为获得干净工作区清除他人改动。

把需求转换成可判断的行为：谁在什么前提下执行什么操作，系统返回什么、改变什么，失败或无权限时应怎样处理。按任务补充权限、数据范围、兼容性和性能约束；没有依据时不要自行编造指标。

区分已确认事实、可逆的实施假设与待确认的业务决策。已能从需求和仓库确定的事项不重复问；金额、权限、删除语义、用户可见行为等关键歧义未解决前，不实现依赖该答案的部分，继续独立调查。用户要求实际开发且信息充分时自行推进，不新增固定的“方案审批”环节。

验收场景尽可能表述为“给定前提 → 执行动作 → 可观察结果”，覆盖主要成功条件和风险相关的拒绝/失败条件。仅要求方案时，交付需求理解、缺口与实现建议即止，不进入编码。

## 2. 调查现状与功能缺口

项目已有代码知识图谱且需要分析复用、调用链或变更影响时，按[知识图谱增强](references/code-knowledge-graph.md)优先查询相关关系，再以当前源码核实；先确认索引与仓库/版本对应，无图谱时按现有源码调查继续。

查找已有能力，沿相关入口追踪到输出、数据写入及外部副作用。修改共享函数或契约前检查调用方，包括适用的后台任务、客户端和重试路径。

涉及接口、数据格式或状态语义变化时，识别生产者与消费者，核对权威定义、实际调用和兼容要求；生成物按项目维护方式更新并验证一致性。需要分批切换或新旧版本共存时，明确兼容窗口和切换顺序。仅在实际需要时引入兼容处理。

确定规则、编排、状态及副作用的现有归属，选择最小正确改动位置。修复缺陷时先复现或取得足以定位的诊断证据，避免只修一个入口而遗漏同源调用方；无法复现时明确证据限制，不伪称已复现。

进入编码前，改动位置与验收方式应对应；若现有能力已满足需求，说明证据，不另造实现。

对每项需求判断属于：已满足、部分满足、缺失或待核实，并给出源码、测试、配置或运行证据。不能仅凭搜索未命中断定缺失；检查命名别名、路由接线、开关、权限、已有服务及调用方。

明确差距在哪里：能力不存在、已有能力没有接线、权限/配置阻断、实现缺陷，还是仅缺少测试或运行证据。代码存在但未部署、未启用或未经真实路径验证，不能表述为用户已经可用。

非平凡任务在编码前提供简短映射，默认在会话中表达：

| 需求/验收场景 | 当前行为与证据 | 缺口 | 可复用能力 | 最小改动与验证 |
|---|---|---|---|---|
| 本次具体行为 | 文件/符号、配置或检查结果 | 已满足/部分满足/缺失/待核实及原因 | 现有入口/服务/组件/查询/测试 | 改动归属和能证明成功的检查 |

简单修复可用一段话表达同样的信息；不强制为每个任务生成文档或填无关字段。

## 3. 确定复用与最小实现方案

先判断是否需要新增代码，再依次考虑已有能力、配置或接线、标准库/平台能力、已安装依赖，最后才新增必要实现。复用前核对语义、权限、数据所有权、错误行为、事务和性能约束，不能只因名称相似就调用。

方案应简述：具体改变什么、保持什么、复用哪些位置、在哪里新增必要逻辑、受影响调用方、如何验证；只有涉及迁移或有状态变更时才补充必要的回滚/兼容步骤。

只有存在真实取舍时比较方案，不为凑选项制造三套设计。选择满足完整验收要求、符合业务归属且新增复杂度最少的实现；最小实现不等于删掉错误处理、安全措施或把逻辑塞入无关公共类。若需要扩大范围或新增依赖，先说明现有能力不足的证据及影响。

编码前自检：需求结果可验证、缺口有证据、复用候选已核实、改动归属明确、关键业务歧义已解决。尚不明确时继续有针对性调查或最小实验，不凭假设铺开实现。

### 编码前的分支检查

维护 Git 项目时，在首次修改前确认实际分支、项目指定基线与任务范围。普通任务避免夹带未选入的工作；候选或已发布版本的修复以实际受影响版本为依据，按项目规则选择起点和同步目标。已有任务分支核对归属后复用，具体分支操作遵循项目约定。角色不明时先查依据，只询问仍无法确定的必要选择，同时继续独立分析。

已有无关改动时保留它们，必要时使用隔离 worktree。仅分析不编码时不必创建分支；无 Git 的任务跳过。由 `delivery-workflow` 调用本技能的分析阶段时，只执行需求、缺口和方案分析，返回编排流程完成建分支检查后再编码。切换基线后重新核对受影响的现状判断，不能沿用其他分支的调查结果。

## 4. 按可验证结果安排步骤

复杂任务按完整业务路径或可独立验证的行为拆分，每步明确结果、依赖和验证方式。必要的基础改动服务于最近的业务步骤，不先一次性铺满所有技术层。

优先验证最不确定的关键假设。首条路径用于检验实现方式，验证后继续完成其余范围，不把示范路径当成任务完成。

计划默认在会话中表达；只有项目要求、用户要求或持续执行确有需要时才落盘。代码和架构标准引用项目约定，不在计划中复制一套规范。

## 5. 每步完成闭环

### 代码规范与必要注释

最小实现以满足需求且易于理解、修改和验证为准，不以字符或文件最少为目标。“优雅”落实为命名准确、职责清楚、控制流直接、边界明确，与项目既有惯例一致。

- **遵循项目规范**：读取适用的命名、目录、格式、类型及错误处理约定，复用相邻代码中的成熟写法和已有 formatter/lint/类型检查。没有规定时采用语言惯用写法，不另造规范工具或为统一风格重排无关代码。
- **直接表达意图**：名称体现领域含义，涉及单位、状态或边界时明确语义；函数围绕一个清晰职责组织，控制流和副作用顺序可追踪。避免难读的嵌套表达式、隐式状态及吞掉错误；不为压缩行数牺牲可读性，也不为缩短函数机械拆分。
- **克制抽象**：优先现有能力和标准库；新增抽象须解决当前的语义重复、职责隔离或明确契约需求。不为假想扩展预留配置、包装层、工厂或通用框架；外形相似但语义不同的逻辑不强行共用。必要的边界校验、错误处理和资源释放不能因“最小化”省略。
- **注释解释原因和约束**：对无法从命名和类型直接看出的不变量、顺序要求、单位/协议约束、兼容原因及非显然取舍，在相关代码旁写清。公开接口按项目约定记录调用者需要的前提、返回/错误及副作用；不逐行翻译代码，不要求每个函数都有注释。
- **注释随代码维护**：行为或契约变化时同步更新注释与相关文档，清除误导说明及本次引入的死代码、调试残留和注释掉的旧实现。必须保留的临时绕行写明原因及移除条件，按项目惯例关联问题；不留无行动依据的 TODO，不记录敏感信息。

每步复核实际 diff：上述适用项有无违反、注释是否与行为一致、新增层次是否必要。工具检查负责可自动检查的规则；命名、职责和注释语义由审查结合源码核对。必要时按需使用已有 `code-simplification`，保持行为不变；不得把它变成每次必跑的全仓重构。

### 实现与验证

开始编码前，确认需求结果、改动位置和能区分成功与失败的验证方式已明确。这是 agent 自检，不增加用户审批。

对每个步骤依次执行：

1. 先确定检查输入、预期结果和关键失败情况。缺陷修复条件允许时先让回归检查在旧实现上因原问题失败；重构先确认相关行为基线。无需每次运行全量检查。
2. 复用现有能力，完成满足该步骤的最小实现。
3. 使用项目已有方式执行验证。非平凡逻辑保留能捕获回归的可运行检查；简单文案或机械修改采用相称检查，不为了流程添加测试。不能为迁就实现而降低原验收要求。
4. 检查完整差异和受影响调用方，处理本步引入的重复逻辑、错误归属和临时残留。

当前步骤验证通过且本步结构问题已处理，才进入依赖它的下一步。后续修改影响已验证步骤的假设、行为或依赖时，立即将相关验证标为待执行，重跑受影响检查；未受影响的有效证据可复用。

功能验证和结构复核分别判断：测试通过不代表职责合理，拆短文件不代表结构改善。具体标准遵循项目规则；没有规则时检查重复、归属和修改影响范围，不发明硬阈值或为了分层增加抽象。

涉及事务、锁、幂等、事件、批处理、重试时，核对改变前后的关键顺序和失败结果，跨真实边界验证必要的不变量，不能只比较最终成功输出。

若实现必须不断扩大同一对象、函数或模块的职责，先重新判断归属，选择在本步内调整、缩小步骤或修改方案，再继续。整理到本步边界清晰、验证通过即停止；不顺手展开全仓重构，也不以“以后统一重构”为由积累本步问题。测试代码一起检查归属，避免将负担转移到巨型测试文件。

## 6. 失败与变更时如何继续

| 发现 | 后续动作 |
|---|---|
| 已有能力可以复用 | 缩小方案，删除不再需要的新实现 |
| 测试或运行结果不符 | 保留证据，定位原因后修复；同类尝试没有新证据时停止改代码，重新检查假设、缩小复现或增加观测 |
| 结构假设错误 | 返回改动位置或步骤设计，调整后继续，不叠加适配层掩盖问题 |
| 无关旧问题或需求扩大 | 区分本次阻碍与额外工作；新增范围需要用户决定时继续独立工作 |
| 缺少环境、凭证或外部条件 | 寻找能证明同一验收条件的替代验证；仍缺证据时记录恢复条件，推进独立部分，受影响步骤保持受阻 |
| 检查无法执行或读取输入失败 | 报告检查未完成，不能当作零问题或通过 |

每次重试都应有新依据；涉及外部写入时，先确认上次是否已生效及是否可安全重试，避免重复副作用。

验证手段可以调整，验收标准不能随之降低。说明替代证据覆盖什么、不能证明什么；静态检查、替身测试和真实集成验证不能互相冒充。

需要记录进度时，区分“已实现”（改动已存在）、“已验证”（对应检查通过）、“受阻”（缺少必要条件）和“已交付”（约定终点已满足）。可同时记录已实现但验证受阻；用简短会话记录保留证据、恢复条件和下一步，不另建状态管理体系。

## 7. 整体复核与交付

对照原始需求检查端到端连接、受影响调用方、关键失败路径和临时实现清理情况。运行项目要求的适用检查。交付前，每项需求应有与最终代码对应的证据；证据缺失的项目明确标为未验证，不宣称全部完成。

进入提测或发布流程时，交接“需求/验收场景 → 最终版本检查结果”的对应关系，按同包 `delivery-workflow` 的交付质量门禁判断是否可推进。必改项未解决、关键检查失败或缺证据时停在对应关卡；不能通过缩减原验收要求、降低阈值或只展示成功用例宣称完成。

合并或解决冲突后验证最终组合结果，不能直接沿用合并前记录。证据保留对应代码状态、检查范围和环境的简短说明即可。

项目有专项 skill 或守护工具时，在对应步骤使用其实际能力；不默认依赖其他 skill，也不把所有专项流程叠加到每个任务。

本技能包含完整的基础开发步骤，可独立执行；以下能力仅按需要从当前技能目录读取，不因缺少可选技能而跳过基础验证，也不宣称执行过未加载的专项流程：

| 场景 | 可组合技能 |
|---|---|
| 非平凡行为或回归保护 | `test-driven-development` |
| 失败或根因不明 | `debugging-and-error-recovery` |
| 接口/责任边界变更 | `api-and-interface-design` |
| 复杂任务分步推进 | `planning-and-task-breakdown`、`incremental-implementation` |
| 结构重构、安全、性能专项 | `structured-refactor-workflow`、`security-and-hardening`、`performance-optimization` |
| 完整代码审查 | 同包 `code-review-workflow` |
| 分支、提测、验收和正式 MR | 同包 `delivery-workflow`，从其当前阶段继续，不重新启动开发流程 |

提交、推送、创建 MR/PR、合并、部署遵循项目规则与用户已授权范围。流程进入下一阶段不产生额外授权，已有授权不重复询问。发布在范围内时，按项目实际流程验证版本和业务行为；状态码、进程存活或 CI 成功不能替代业务验收。

交付简述实际改变、验证结果和重要限制，如实标明部署与业务验收状态。约定终点满足后停止，不再无依据地扩展范围或重复检查；存在阻碍时明确未完成项及恢复条件，不以“建议下一步”替代仍可执行的已授权工作。
