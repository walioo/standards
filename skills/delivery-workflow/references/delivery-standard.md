# 代码开发与交付工作流规范

适用于维护项目的新功能与缺陷修复。本文定义流程；每个仓库在自己的 `AGENTS.md` 中明确正式基线、测试目标、命令、门禁与发布权限。已有仓库规则不被本文静默覆盖，执行前解决实际冲突。

## 分支流向

### 先选择适用路径

- **业务运行变化**：遵循下方正式基线 → 任务分支 → 测试 MR/环境验收 → 正式 MR 的完整流程。
- **纯文档或规范变更**：确认不改变程序、构建、部署、权限或数据行为；目标仓库未要求测试环境时，可从正式基线建任务分支，经内容审查、格式/链接及适用示例检查后，直接向正式目标提 MR。没有 dev/test 时不创建虚构测试分支，不要求业务部署 SHA 或测试环境验收。记录本次实际文档检查证据，运行/发布门禁注明不适用及理由；分支保护、审查必改项和合并授权仍然生效。
- 不能仅按文件扩展名判定：CI YAML、数据库迁移、可执行脚本以及会改变工具操作的技能规则需要相应行为验证。skill 的声明式规则变更可采用隔离场景验证，不强制业务环境；若引入实际运行副作用，应走相应运行验收。
- 仓库明确要求更严格流程时遵循仓库规则；混合变更按业务运行路径处理。适用性无法确认时先调查，不能自动选较弱路径。

```text
最新 origin/main 或 origin/release（仓库指定的正式基线）
  └─ feat/业务描述 或 fix/问题描述
       ├─ MR → dev 或 test → 部署测试环境 → 测试验收
       └─ 验收通过后，同一功能/修复分支 MR → release 或 main
            └─ 正式 MR 合并并核实 → 删除已完成的功能/修复分支
```

`main/release`、`dev/test` 是仓库配置的角色选项，不表示随意二选一或需要同时提交多个目标。有 `release/*` 的项目应明确本次具体版本分支，以及 release 到 main 的同步方式。

## 1. 开始任务与创建分支

1. 使用同包 `development-workflow` 澄清需求与验收场景，确认实际仓库、适用规则及工作区改动。调查现状和功能缺口，核实可复用能力、业务归属、完整调用链及副作用，再确定最小实现方案和改动位置；简单任务可简述，不强制生成长文档。
2. 按仓库允许的远端访问方式刷新引用，确认最新正式基线 SHA。从该 SHA 创建本地任务分支；不要从含其他未发布功能的 dev/test 开始维护任务。
3. 工作区已有无关改动时保留它们，必要时创建隔离 worktree，不清理或覆盖他人工作。
4. 一个分支对应一个可独立测试和交付的功能或问题。命名描述业务意图，可附工单号：

   - `feat/course-category-filter`
   - `fix/order-refund-duplicate`
   - `fix/TS-123-login-timeout`

分支名、提交信息和 MR 标题不加 `ai`、`codex`、`claude`、`agent`、`generated` 等作者/工具标签，也不使用无业务含义的 `update-code`、`fix-bug`。真实业务名称含 AI 时可以正常表达，例如 `feat/ai-search`。

## 2. 开发与本地验证

以 `development-workflow` 为开发入口；本工作流只安排阶段，不复制各 skill 的完整规则。

| 场景 | 使用的 skill | 产出或检查点 |
|---|---|---|
| 所有开发任务 | `development-workflow` | 明确行为、最小正确改动位置、分步验证与交付状态 |
| 行为变化与缺陷修复 | `test-driven-development` | 有效行为断言；修复尽可能证明旧实现失败、新实现通过 |
| 根因不明、测试失败 | `debugging-and-error-recovery` | 根因证据，避免只处理症状或盲目重复尝试 |
| 接口或模块契约变化 | `api-and-interface-design` | 调用方、兼容性、责任边界明确 |
| 多步骤复杂任务 | `planning-and-task-breakdown`、`incremental-implementation` | 按完整可验证行为推进，不预建无需求的框架 |
| 结构重构 | `structured-refactor-workflow` | 行为保持、职责归属与结构验收 |
| 权限、输入、敏感数据、外部调用 | `security-and-hardening` | 信任边界、拒绝路径与敏感数据保护 |
| 性能风险或性能目标 | `performance-optimization` | 同条件基线、测量与回归证据 |
| 提交测试 MR 前与正式 MR 前 | `code-review-workflow` | 覆盖率、正确性、质量、架构、安全、性能、兼容性与验证缺口 |

按需要加载技能，不要求每个任务运行所有技能。优先复用仓库已有实现、标准库、工具链和测试；不因流程增加依赖、层次或全仓重构。

验证重点：

- 非平凡行为留下能捕获回归的可运行检查；覆盖正常、边界和必要的失败路径。
- 覆盖率按仓库阈值与真实统计范围检查，同时审查关键分支与断言有效性，不能仅凭高百分比放行。
- 执行适用的格式、静态检查、类型检查、构建、测试及专项门禁；命令来自仓库配置和 CI。
- 评审发现按风险与证据处理；可选风格建议不阻断，必改项处理后再进入测试交付。

## 3. 提交测试 MR

1. 检查 Git 身份、当前分支和完整差异，仅提交本次文件；遵守仓库的提交与远端访问规则。
2. 推送任务分支，确认与测试目标存在有效差异，创建 `任务分支 → dev/test` 的 MR。
3. MR 写明问题与结果、影响范围、验证结果、测试步骤和必要的回滚说明，不使用工具署名或空泛标题。
4. **测试 MR 不启用合并后删除源分支。** 正式交付仍需要原任务分支。
5. 按项目授权和 CI/CD 流程合并、部署测试环境；记录实际部署版本。MR 已合并或 CI 成功，只能说明相应步骤完成，不能替代测试验收。

### 测试目标冲突

不要把 dev/test 合并回将来要发布的任务分支，否则可能夹带其他未验收功能。

若测试 MR 无法直接合并，从任务分支建立临时 `integration/业务描述-test` 分支，在其上合并测试目标并解决冲突，再以该集成分支向测试目标提 MR。原任务分支保持只含正式基线与本任务变更。测试环境适配只留在集成分支；业务修复要落实回原任务分支并重新测试。

这类任务的验收证据应同时记录原任务 SHA、集成 SHA 和环境版本；测试环境的组合结果不能自动证明正式目标组合也正确。

## 4. 测试验收关卡

验收至少记录：任务分支 SHA、测试环境/部署 SHA、验收场景、结果、测试负责人或可追溯的验收记录，以及未解决问题。

- 测试未通过：在原任务分支修复，重新交付测试。若原测试 MR 已 merged/closed，新增测试 MR，不向旧 MR 假装追加验收结果；先确认新改动相对测试目标确实有差异。
- 测试通过：才允许创建正式目标 MR；测试阶段不提前创建正式 MR，包括草稿 MR。
- 验收后新增改动、更新正式基线或解决冲突：标记受影响证据失效，重新验证受影响场景及仓库要求的检查。不能沿用旧版本的通过结论。
- 等待验收是明确的流程状态；开发者或 agent 不能以单测通过替代测试负责人的业务验收。项目已明确认可的自动化验收可按其规则执行。

## 5. 正式 MR 与发布

1. 验收通过后刷新正式目标，检查原任务分支的提交与差异只包含本次内容。默认使用原任务分支创建 `任务分支 → release/main` 的 MR，不使用 dev/test 作为发布来源。
2. 若正式目标已变化，在原任务分支同步最新正式目标并解决冲突；使用仓库允许的方式，避免覆盖协作者提交。验证最终合并组合，必要时重新走测试验收，再创建或更新正式 MR。
3. 正式 MR 关联测试 MR 和验收记录，注明已验收任务版本、检查结果、发布注意事项与回滚方式。
4. 执行最终 `code-review-workflow` 和仓库必需 CI；解决必改项，关键验证缺失时不得宣称可以合并。
5. 合并、发布仍遵循项目角色权限和用户已有授权。流程规范本身不授予对任意仓库执行合并或生产部署的权限。
6. 合并成功不等于已经部署。发布在本次范围内时，核对上线版本和真实业务路径；不在范围内时明确“已合并，待发布”。

## 6. 分支清理与关闭

- 正式 MR 合并后，核实本任务完整变更已进入正式目标、没有待使用该分支的 MR 或未提交/未推送工作，再删除对应远端与本地任务分支；清理已无用途的本任务集成分支。
- 若还有明确要求的其他正式目标待同步，先完成同步，不能因第一个 MR 合并就提前删除。
- 删除前确认 worktree 使用情况；先切换到适当保留分支，或安全处理已完成任务的 worktree，不强删含工作内容的目录。
- squash/rebase 合并后，Git 可能无法通过祖先关系识别已合并；结合 MR 状态、合并结果和最终内容核实，不能直接用强制删除绕过检查。
- 已删除分支后发现新问题，从最新正式基线新建 `fix/问题描述`，重新走流程。

## 交付质量门禁

在需求澄清时确定验收条件，在对应交付阶段逐项复核。复用测试、CI、审查和验收记录，不要求另建评分系统或重复跑未受影响的检查。每项状态只能是通过、失败、未验证或不适用；不适用需要依据，不能作为跳过困难检查的理由。

| 关卡 | 通过所需证据 | 阻断条件 |
|---|---|---|
| 可提测 | 约定提测范围内的需求都有实现位置与验证结果；关键入口接线完成；仓库必需检查通过；审查必改项已处理 | 主路径未接通、临时桩/硬编码冒充完成、相关检查失败、关键回归无证据或必改项未关闭 |
| 可正式合并 | 最终任务版本有测试验收记录；核对正式目标的完整差异与最终合并组合；需求、接口/配置说明与代码一致；适用审查和 CI 通过 | 验收版本与当前变化不匹配、夹带未验收功能、正式组合未验证、关键风险仍未解决 |
| 可发布 | 发布在授权范围内；已核实产物与批准代码版本对应；必要配置、依赖和迁移顺序明确；适用的回滚/恢复路径可执行 | 产物版本不明、配置/迁移前提缺失、可能破坏数据但没有恢复措施 |
| 发布验收完成 | 实际线上版本和关键业务路径验证成功；按项目约定检查错误、延迟及数据一致性等指标；异常有明确处理结果 | 只有进程/状态码正常、只有部署成功、真实业务未验证，或存在新回归尚未处理 |

质量检查覆盖以下内容，并按变化选择深度：

- **需求完整性**：逐项对应验收场景，确认成功结果、边界、失败/拒绝路径及必要副作用。分批提测必须明确本批范围和未交付项，不能据此宣称全需求完成；缩减已承诺范围须有用户或需求负责人的明确决定。
- **测试有效性**：断言应能捕获业务回归；关键权限、资金、事务、幂等与并发风险有相应检查。覆盖率沿用仓库口径，不能通过删测试、跳过失败、修改阈值或排除源码制造通过。
- **代码与专项质量**：检查职责归属、复用、可维护性和本次新增复杂度；安全与性能按风险提供证据。具体检查由 `code-review-workflow` 执行，不以代码格式整齐替代质量判断。
- **真实集成**：涉及跨模块/API/数据库/外部服务的变化，验证必要契约和接线；mock 单测不能冒充真实集成。外部环境无法使用时写明证据缺口，阻断依赖该证据的关卡，继续独立工作。
- **可运维与交接**：适用时同步接口、配置、迁移和使用说明，错误信息可定位且不泄露敏感数据。发布前写清操作顺序、验证方式和回滚触发条件；不可逆数据变更需要明确备份/恢复或经授权的前向修复方案，不能只写“回滚代码”。

证据必须能关联到提交 SHA、产物版本或实际部署状态，并记录检查范围、环境和结果。CI 指向旧 SHA、代码通过但产物不对应、验收后又修改代码时，相关结论失效；先补验证再放行。非阻断建议可保留，但需说明原因、责任人与跟进条件；必改项和缺失的必需验证不能包装为“后续优化”。

每次交付在 MR 或已有任务记录中保留下面的简短内容，可链接已有报告，不另建重复文档：

```text
交付范围与阶段：本次完成什么，当前是提测/待验收/待合并/待发布/已发布验收
版本：任务 SHA、目标分支、MR；适用时补充产物与环境版本
需求与证据：验收场景 → 检查/报告 → 通过、失败、未验证或不适用
审查结果：必改项处理状态，非阻断风险及处理依据
剩余事项：缺失证据、负责人、解除阻碍的条件；无则明确写无
发布交接（适用时）：配置/迁移顺序、验证方式、回滚或恢复依据
```

只有本次约定交付终点的必需项全部满足，才报告该阶段完成。规范本身不等于自动强制执行；需要机器阻断时，在目标仓库已有 CI/保护分支中配置对应门禁，不能宣称安装 skill 就已启用这些控制。

## 仓库落地配置

每个仓库在 `AGENTS.md` 中维护这些具体值，通用 skills 保持跨项目、跨语言：

| 配置 | 内容 |
|---|---|
| 正式基线/正式 MR 目标 | `main`、`release` 或具体 `release/*`；多个正式分支时注明同步顺序 |
| 测试 MR 目标 | `dev` 或 `test`，以及对应测试环境 |
| Git 与 MR 规则 | 身份、远端访问方式、命名、合并方式与保护分支权限 |
| 工程门禁 | 实际构建/测试/覆盖率/静态检查命令与阈值 |
| 验收依据 | 测试负责人、验收记录位置和业务场景 |
| 发布与清理 | 发布负责人/方式、回滚依据、源分支保留与删除时机 |

状态交付统一区分：开发中、已本地验证、测试 MR 待合并、测试环境待验收、已验收、正式 MR 待合并、已合并待发布、已发布验收、分支已清理。仅报告实际到达的状态。
