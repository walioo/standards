# 代码开发与交付工作流规范

本文定义阶段、输入输出和放行条件。项目通过 `AGENTS.md` 明确交付模型、基线、命令、角色与验收要求；具体工具和自动化由项目实现。

## 适用范围与职责

| 层级 | 维护内容 |
|---|---|
| 通用工作流 | 范围确认、基线选择原则、开发与审查、验收关卡、版本追溯、异常处理、交付状态 |
| 项目规则 | 分支与环境映射、检查命令、阈值、责任人、专项约束、恢复与同步方式 |
| 执行机制 | CI、自动合并、构建部署、测试隔离及业务实现 |

项目实现缺口记录在该项目的接入或任务清单中，不因单个项目的问题向通用规范增加固定工具、业务规则或全局门禁。规范接入不代表自动化已配置或实际行为已验收。

## 选择交付路径

先确认用户要求的终点和项目已有模型，不要求所有任务经历所有阶段。

| 路径 | 适用情况 | 最小闭环 |
|---|---|---|
| 分析或审查 | 用户只要求方案、调查或审查 | 范围与证据 → 结论及缺口，不自动编码或交付 |
| 简单变更 | 局部、低风险，或不影响运行行为的文档变更 | 最小修改 → 相称检查与复核 → 约定终点 |
| 单任务交付 | 项目按独立任务验证和交付 | 项目基线 → 任务实现与审查 → 适用验收 → 正式交付 |
| 批次交付 | 多个任务需选择性或协同发布 | 项目基线 → 任务验证 → 组装选定范围 → 组合验收 → 正式交付 |

按影响判断路径，不只看文件数量或扩展名。配置、迁移、可执行脚本及技能规则也可能改变行为；采用能证明该变化的验证，不强制部署到业务环境。简单路径可以合并步骤，但不得省略适用的安全、数据或兼容性检查。

批次交付不强制增加环境或分支。项目可配置开发、预发布、生产等阶段；环境数量、命名和候选版本的承载方式由项目决定。

## 1. 确认范围与基线

使用 `development-workflow` 明确需求、当前证据、缺口、复用位置、最小改动和验收条件；简单任务简述即可，不要求额外计划文档或固定方案审批。

- 识别实际仓库和适用规则，多仓库分别确认工作区、目标与依赖；保护已有改动。
- 从项目指定的权威基线开始普通任务，核对版本和范围，避免夹带不属于本任务的工作。刷新失败时说明版本限制，不能把缓存引用称为最新。
- 修复候选版本或已发布版本时，以实际受影响版本为依据，按项目规则选择修复基线及同步目标，不把例外变成普通任务默认路径。
- 已有任务分支或有效证据可继续使用，核对归属后复用，不重复创建。无版本控制时跳过分支操作。
- 分支、提交和变更请求名称描述实际变化，遵循项目命名规则，不附加工具署名。

用户已明确的授权和项目规则继续有效；只询问影响正确性或范围且无法调查确认的歧义，继续不依赖答案的工作。

## 2. 开发与审查

使用 `development-workflow` 完成实现与相关检查，再由 `code-review-workflow` 复核。调试、接口、结构、安全、性能等专项按风险加载，不要求每次运行全部技能。

- 复用已有实现、工具链和检查，非平凡行为保留能捕获回归的验证。
- 检查命令、覆盖范围和阈值来自项目；先核实执行副作用和环境，区分只读检查与自动修改。
- 审查沿受影响调用链，验证正确性、兼容性及必要副作用；问题按证据、影响和是否必改分类，个人风格不阻断。
- 开发、审查和验收共享有效证据；版本、范围、配置或依赖变化后，重新验证受影响部分。未变化且适用的证据不重复采集。

## 3. 提测与组合验收

按项目方式提交可追溯的候选版本，写明范围、影响、已执行检查及待验收场景。需要后续交付的任务分支或产物不能在提测后提前删除。

单任务路径验证本任务及必要集成；批次路径另需满足：

1. 明确选入和未选入范围，识别依赖关系。不能独立交付的变化一起验收或整体延后。
2. 以最终组合的实际内容为准，核对没有未选入的变化，不能只依赖任务列表、分支名或合并状态。
3. 冻结本轮验收对象并记录版本。新增任务、修复或冲突解决改变对象时，重新确定范围并验证受影响场景。
4. 多仓库记录各组件版本及必要的配置、依赖顺序和验收结果；单个组件通过不代表组合通过。

验收至少记录对象版本、场景、环境或条件、结果和可追溯的验收来源。人工验收或自动化验收按项目认可的方式执行；局部单测、构建或部署成功不能替代业务验收。

## 4. 正式交付与发布

- 正式交付来自已验收的任务或批次，核对最终差异与目标组合；正式目标推进时评估影响，不能直接沿用不再适用的结论。
- 必改项和必需检查满足后，按项目规则与已有授权推进合并和发布。是否允许提前创建草稿变更请求由项目决定，创建草稿不能代表已具备合并条件。
- 发布对象必须与验收对象可追溯对应。采用构建产物晋级时复用已验收产物；需要重新生成时证明对应关系，并执行项目要求的重新验证，不能自动继承旧验收。
- 核对适用的配置、依赖、数据变更及恢复前提；具体迁移、部署和回退机制来自项目，不在本流程统一指定实现。
- 发布后验证实际版本与关键业务结果。合并、部署、运行存活和业务验收分别报告，不互相替代。

发布不在任务范围时，完成已授权终点并明确待发布状态，不自动扩大到生产操作。

## 5. 异常与恢复

| 情况 | 必须保持的约束 |
|---|---|
| 合并冲突或目标变化 | 保留原工作，确认最终范围与语义，重新验证受影响组合；具体合并、隔离或同步操作遵循项目规则 |
| 取消任务后重新纳入 | 以实际内容核实取消和恢复结果，不能把历史合并记录当作功能已恢复；重新确认依赖与验收 |
| 候选版本修复 | 修复进入实际待交付对象，并按项目规则同步受影响维护线，验证最终组合 |
| 紧急修复 | 基于实际受影响版本，明确独立修复范围、验证与恢复依据，不夹带无关候选；共享环境占用和缩短流程按项目应急规则处理 |
| 检查失败或条件不足 | 区分实现错误与环境/证据缺口，阻断依赖该条件的关卡，继续独立工作，不降低验收标准 |
| 外部动作结果不明 | 先确认是否生效及重试是否安全，再决定继续；避免重复副作用 |

紧急情况不自动授予额外权限。同步与恢复完成后再核对版本和证据，不把“已处理冲突”或“已回退”直接表述为业务已恢复。

## 6. 清理与交接

按项目留存规则，确认约定交付完成、必要同步结束，没有活动依赖或未保存工作后，清理已无用途的临时分支和工作区。保留仍需使用的版本标识、产物及验收记录，不强制所有项目采用相同删除时点。

在已有变更请求或任务记录中交接，不另建重复状态系统：

```text
范围与阶段：本次完成内容及实际到达的交付阶段
版本：任务/候选/正式对象标识；适用时关联产物、配置和环境
需求与证据：验收场景 → 检查/报告 → 通过、失败、未验证或不适用
审查结果：必改项处理情况、非阻断风险及依据
剩余事项：缺失证据、责任人和继续条件；无则写无
发布交接（适用时）：必要顺序、验证方式和恢复依据
```

## 交付质量门禁

| 关卡 | 通过依据 | 阻断条件 |
|---|---|---|
| 可提测 | 约定范围已实现，关键接线完成，适用检查与审查通过 | 主路径不完整、关键回归无证据、必改项未处理 |
| 可正式合并 | 最终变化与验收对应，目标组合已验证，项目必需门禁满足 | 夹带未验收变化、版本或证据不匹配、关键验证缺失 |
| 可发布 | 已获授权，发布对象可追溯，配置/依赖/数据及恢复前提明确 | 对象不明、前提缺失，或数据风险没有可执行处置方案 |
| 发布验收完成 | 实际版本、关键路径及项目要求的运行结果得到验证 | 只有构建/部署成功或进程正常，业务结果未验证 |

代码改动的审查须包含[代码规范与必要注释](../../development-workflow/SKILL.md#代码规范与必要注释)：项目适用工程检查有结果，代码及注释的必改项已处理。规范文件本身不等于自动化保障；缺少检查能力时如实记录，不凭测试通过省略可维护性复核。

项目可不使用某个阶段，但须根据任务影响说明适用性；不能以“不适用”跳过困难检查。必改项和必需证据缺失不能被其他通过项抵消。有效证据持续复用，只因新增变化、失败或尚未解决的疑点补充验证。

## 项目接入配置

项目 `AGENTS.md` 或其引用的权威文档维护以下实际值：

- 交付模型、基线和目标角色；适用的分支、环境及版本映射。
- 工程命令、范围、阈值、执行副作用及必要专项要求。
- 审查与验收方式、责任人、证据位置及版本关联。
- 发布授权、依赖顺序、恢复与同步方式、留存和清理条件。
- 自动化接入的结果协议、必需门禁和权限来源（适用时）。

定义要求与实现要求分开验收。流程执行、CI 强制门禁及真实发布是不同能力，不能宣称安装规范即已具备全部能力。
