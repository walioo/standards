# 开发交付工作流

在本工作流调用依赖技能时，依赖提供实施方法；阶段、执行范围和验证深度以当前工作流、用户要求及项目规则为准。依赖中的全量测试、运行验收、文档更新或暂停要求先判断适用性，不因加载依赖就一律执行；项目明确的必需检查、安全约束和授权边界不得省略。

读取[交付规范](references/delivery-standard.md)，按任务影响和项目规则选择路径，完成用户要求的交付终点。本文负责阶段编排，开发由 `development-workflow` 执行，审查由 `code-review-workflow` 执行。

## 确认现场

- 确认实际仓库、需求范围、项目交付模型、当前阶段、基线/目标角色及已有授权。
- 涉及组件依赖或跨仓库交付时，按[知识图谱增强](../development-workflow/references/code-knowledge-graph.md)复用可用的关系与影响分析；交接关联版本及验证缺口，不能用图谱连通代替组合验收。
- 检查已有工作和证据；续接任务复用仍然有效的结果，不重复建分支、变更请求或验证。
- 项目可采用简单变更、单任务或批次交付，不强制三环境、候选分支或固定工具。仅分析/审查时止于相应结果。
- 具体映射先从项目规则查明；缺少影响正确性的决定时询问，同时继续独立调查。不得凭分支名称猜测角色或覆盖已有工作。

## 阶段与产出

| 阶段 | 执行 | 进入下一阶段的依据 |
|---|---|---|
| 范围与方案 | 明确需求、当前证据、缺口和最小方案 | 结果可验证、归属明确、关键歧义已解决 |
| 开发 | 核对基线，使用开发工作流实施与验证 | 约定行为完成，相关检查有证据 |
| 审查与提测 | 使用审查工作流，提交可追溯候选 | 必改项处理完成，适用门禁满足 |
| 验收 | 按项目方式验证任务或最终批次组合 | 验收对象、范围、条件和结果明确对应 |
| 正式交付 | 核对最终差异和目标组合，按授权合并/发布 | 必需验证满足，交付对象可追溯 |
| 清理与交接 | 完成必要同步和留存检查，报告实际状态 | 无待使用依赖或未保存工作，约定终点满足 |

简单任务可以合并步骤，保留适用门禁即可；复杂任务按风险增加验证深度，不增加固定审批层或文档数量。

## 执行约束

- 按[交付质量门禁](references/delivery-standard.md#交付质量门禁)判断当前阶段，不以构建、合并或部署成功替代业务验收。
- 发布范围只包含已选定和验证的变化；多组件以最终组合验收，不能由单组件结果替代。
- 版本、配置或依赖改变后，评估并重验受影响部分；未受影响且仍适用的证据继续使用。
- 冲突、取消后恢复、候选修复和紧急修复按规范中的异常约束处理，具体操作遵循项目规则。
- 合并、发布和外部动作沿用已有授权；阶段推进不产生额外权限，已有授权不重复询问。
- 只加载当前需要的技能，不默认全部运行或启动多代理。规则、工具或环境缺失时明确限制，继续能独立完成的工作。

等待外部验收时，交接当前版本、所需证据和继续条件；不能自行判定通过。约定终点满足后停止，不无依据扩大范围。

用户要求定时确认、夜间持续实施或次日交接时，读取[定时确认与夜间持续跟进](references/overnight-follow-up.md)。提醒与持续执行分别授权；未回复不构成新目标授权。
