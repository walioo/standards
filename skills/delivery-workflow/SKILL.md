# 开发交付工作流

负责分支生命周期和交付关卡，复用现有开发与审查技能。执行前读取 [交付规范](references/delivery-standard.md)，它是本 skill 的完整流程依据。具体分支、命令、身份和工程阈值由目标仓库的 `AGENTS.md`、CI 和已有约定确定。

## 确认现场与当前阶段

- 确认实际仓库、任务范围、交付终点、正式基线、测试目标及已有授权；不要将创建 skill 的工作区当作所有任务的目标仓库。
- 检查当前分支/工作区、远端引用、已有 MR 状态和验收记录，识别任务已到达的阶段。续接任务复用有效证据，不重复建分支或 MR。
- 分支配置可从仓库明确确认时自行确定；若 main/release 或 dev/test 同时存在且没有角色依据，在创建分支或 MR 前询问这个必要选择，继续不依赖该选择的代码调查。
- 若已有任务分支来自 dev/test，先检查相对正式基线是否混入其他工作；不要直接宣称可发布，也不要重置或强推覆盖它。隔离迁移本任务提交时保留原工作并重新验证。
- 遵守用户当前意图：仅要求规范/方案时不开始业务开发；仅要求提测时不擅自发布。已有授权不重复询问，阶段推进不自动授予额外权限。

## 按关卡推进

| 阶段 | 执行 | 进入下一阶段的依据 |
|---|---|---|
| 建分支 | 从仓库指定的最新正式基线创建 `feat/业务描述` 或 `fix/问题描述`，保护已有工作 | 基线 SHA、任务分支和范围明确；名称不含工具署名 |
| 开发 | 读取并使用 `development-workflow`；按风险加载交付规范列出的 TDD、调试、接口、安全或性能技能 | 本次行为完成，适用本地检查通过 |
| 审查与提测 | 读取并使用 `code-review-workflow`，完成必改项；创建到 dev/test 的 MR，保留源分支 | 测试 MR、检查结果和可部署版本可追溯 |
| 测试验收 | 按授权推进测试部署，核对实际环境版本和验收结果 | 有对应任务 SHA/部署版本的明确验收通过记录 |
| 正式 MR | 仍从原任务分支向 release/main 提 MR，关联验收记录，验证最终组合并复核 | 无未解决必改项，适用门禁和验收满足 |
| 合并与清理 | 按授权完成正式合并，核实变更已进入目标，再清理本任务分支 | 无待完成正式目标、活动 MR 或未保存工作 |

按当前会话技能目录解析并读取所需技能，不硬编码用户主目录。不因编排而加载全部专项技能或启动多代理；依赖技能不可用时明确限制，仍完成有依据且可执行的部分，不伪称执行。

## 不可省略的约束

- 测试 MR 合并后不删除原任务分支；测试验收通过前不创建正式 MR，包括草稿 MR。
- 不把 dev/test 合并回原任务分支。测试目标冲突按交付规范使用临时集成分支；若仓库有冲突处理规则，先解决规则冲突，不静默违背它。
- MR 已 merged/closed 时不继续把新工作当作旧 MR 更新；检查有效差异后按仓库规则创建新 MR，正式发布仍须排除其他任务提交。
- 验收绑定版本；修复、基线同步或冲突解决后重新验证受影响部分。CI 通过、MR 合并和部署成功均不能代替业务验收。
- 分支删除在正式合并核实之后；检查 squash/rebase 合并结果、其他发布目标及 worktree，不强删未保存工作。

## 等待与交付

等待测试负责人验收时，完成仍可独立推进的已授权工作，报告“测试环境待验收”、版本、所需验收证据和下一关卡；不能自行判定通过。只有用户要求后续监控时才设置自动化，不用循环轮询或固定延时冒充验收。

结束时简述当前阶段、任务分支与基线、相关 MR、实际验证/验收结果及剩余阻碍。只报告实际完成的状态；正式合并后尚未部署，明确写“已合并，待发布”。

## 调用示例

`使用 $delivery-workflow 开发这个功能，按仓库正式基线建分支，完成开发审查后提 MR 到测试分支，等待验收。`

`使用 $delivery-workflow 继续这个任务，核实已有测试验收记录，满足关卡后创建正式 MR。`
